## 2. 最小加载前设计

在宿主选择 Skill 前可见的 description 中，增加针对资源定位的规则，例如：

> Use the host-listed Skill path; read the Skill before locating its resources. Do not use host settings or installation receipts for resource lookup.

这补充的是不同披露时点：宿主列出的绝对 Skill 位置足以定位包内脚本，而非先解析安装记录或宿主设置。它与现有主流程中“资源来自安装包，cwd 为授权项目”的规则衔接，不需要新 hook、调度器、扫描服务或自动写项目文件。

边界必须保持：

- 限定 **resource lookup**，不扩大为禁止用户明确授权的安装诊断、配置检查或其他任务。
- 不要求普通项目入口读取一律等待 Skill，也不改变只读、简单任务、宿主规划模式、旧计划权威和禁止新增记录的例外。
- 原有历史访问同意、项目文件恢复及宿主能力披露不能为 description 长度让步而再次删除。
- 这是可验证的模型行为假设，不是访问控制或强制隔离；新产物使用固定任务和模型复验才能判断效果。不得以显式调用或无变更重试代替默认匹配验收。

## 3. 执行、历史与推断的结果分类

最终 `progress.md:26` 将旧命令 `python3 -m unittest tests.test_export_text` 写成改动前“通过”，`:58` 在 Observed 再写“通过（掩盖缺陷）”。但 `:37` 同时说明首次 unittest 在修复后执行；完整原生调用中也没有改动前旧 unittest。

旧测试用 `utf-8-sig` 读回会掩盖 BOM，可以由读码分析解释；该分析不能证明所写命令曾被执行、成功发现测试或返回成功。后来的新测试/旧实现反事实执行也不能补成此前执行证据。

建议沿用现有 entry/evidence 和记录表格，不增加另一套日志体系：

| 来源类别 | 足以支持的记录 | 不应混淆的结论 |
| --- | --- | --- |
| 本次实际执行 | 实际命令或场景、环境、有关输出或错误、可取得的退出状态；据此判断验收要求 | 工具被调用或 exit 0 本身不等于行为正确 |
| 项目历史记录 | 引用来源文件、时点、环境和原有结果/限制，说明本次是否重跑 | 未重跑不使历史 Passed 变成 Not Run；引用不证明历史真实性已独立复验 |
| 静态分析或拟执行 | 标明静态推断/预期与代码依据；对应尚未执行的测试写 Not Run | 不把静态预期放入执行结果栏并称 Observed Passed |

静态检查本身可以记录其检查结果；禁止的是冒充运行测试成功。本次应保留原记录的更正经过，将旧 unittest 条目改为“未执行；根据断言/解码方式推断无法捕获 BOM”。如以后实际补跑，应使用真实新时点，不回填成修复前已执行。
