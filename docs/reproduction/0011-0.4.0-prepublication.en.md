# 0.4.0 stable prepublication acceptance

This record binds the single, not-yet-published `planweft-0.4.0.tgz`. The archive was built from clean content commit `aa23df40f9ec8eaed05aa4fbf6f4f0011709995b` with the release workflow's pinned Node `24.20.0` / npm `11.11.0`, and has SHA-256 `e611338a619adabb0ba943d75460a01d83e4670dbe7d69f5d1050a1c1467c132`. Subsequent commits may add only acceptance material excluded from the npm archive; the archive must be rebuilt in the same packer environment and proven byte-identical before publication. This record does not claim that npm publication or the GitHub Release is complete.

## First publication attempt and correction

The first local review mistakenly used Node `22.22.1` / npm `9.2.0`, producing gzip bytes with SHA-256 `438f164a065e2b57469910580baee3c00aaeac92f1c2c831d1223343bfdb7e4c`. OIDC workflow `34430655159` rejected that mismatch at the exact-artifact check before any npm write: the workflow's Node `24.20.0` / npm `11.11.0` rebuild is the `e611…c132` archive bound by this record. The decompressed tar streams of both archives have the same SHA-256, `b195ce9c9d1a11590e456c613cc22636ab3a30ed118089e55e2036864085b1d0`, proving that the difference is in packer/gzip bytes rather than package content. After the failure, npm still had no `0.4.0`; `next` remained `0.4.0-rc.15` and `latest` remained `0.4.0-rc.1`.

This was handled as the single allowed infrastructure/fixture correction retry. Exact artifacts, five-host installation/removal, user-file protection, actual Skill reading, and the bounded Codex/Pi model workflows that policy forbids reusing were all rerun against the canonical archive, with the same outcomes as the first review. The two semantic failures in the Codex enabled/disabled pair were retained and not retried again. Failed workflow `34430655159` and the old archive digest remain audit history, but neither is the release candidate nor an input to the current acceptance.

Exact artifacts, final installation and removal, user-file protection, and actual Skill reading all use fresh `0.4.0` evidence. Historical reproductions, checkpoints, and failures were not rewritten.

## Known limitations

`LIMIT-CODEX-TRACE-INCOMPLETE`: the predeclared Codex gate-enabled/disabled pair retains two unmodified `Failed` results. The disabled case did not enter the gate; the model returned only `STOP_PROBE`, made no tool call or extra continuation, did not change the project, and completed its session, uninstall, and container cleanup normally. Its native trace nevertheless ended with an unfinished syscall at EOF, so `trace_complete=false`. The enabled trace is complete and attributes the gate reads, but the incomplete negative control prevents the paired assertion from passing. The result is not rewritten to Passed and no additional model retry is performed. It limits the experimental real autonomous/gated stopping claim; it does not negate the passed offline cap/stall/disabled regressions or supported core capabilities.

The Claude, OpenCode, and DSH automatic maintenance, cold-read, context-injection, recovery, and real stopping scenarios remain `Not Run` under this release's bounded model budget rather than being repeated to pursue an all-green result. Their historical results and limitations remain in force. Official-registry lifecycle, new-session loading, and promotion review must be produced after publication to `next`, so they remain `Not Run` at the prepublication stage.

## Evidence and gate

- `evidence/0010/planweft-0.4.0-canonical-prepublication-runs.tar.gz` contains canonical exact-package lifecycle, five-host Skill reading, Codex/Pi workflows, and the original Codex pair results. Maintenance and cold reads also have distinct `canonical` attachments so one digest cannot stand in for both phases.
- `evidence/0010/planweft-0.4.0-canonical-local-checks.tar.gz` contains the complete post-correction Python and `npm run check` logs.
- `evidence/0010/planweft-0.4.0-canonical-rc15-manifest-diff.json` binds RC15 and the canonical target archive file by file and records affected checks and the reviewer.
- `release/acceptance.json` uses schema 3. The gate computes `release_blocking` from `release/support-policy.json`; any required non-Passed result blocks, while experimental non-Passed results require an attachment, reason, and public limitation ID.

Before publication, independent prepublication review, the final gate, Linux/Windows/macOS Check on the same final commit, and a byte-identical archive rebuild must complete. After publication to `next`, the package must be downloaded from the official registry, checked for byte and integrity identity, and exercised through five-host remote installation, discovery, doctor, new-session loading, and removal. Only a subsequent promotion review and gate may authorize moving `latest` and creating the `v0.4.0` GitHub Release.
