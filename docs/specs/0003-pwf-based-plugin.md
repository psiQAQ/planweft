# SPEC-0003：PWF 底座的多平台文档协作插件

状态：Accepted；日期：2026-09-08。需求来源：用户明确批准并要求实施的 Program Design 0.2.0 计划。实现与验证状态以 [PLAN-0005](../plans/0005-pwf-based-plugin.md) 和 [REP-0005](../reproduction/0005-pwf-based-plugin.md) 为准；本文件的 Accepted 不代表验收通过。

## 目标与替代范围

以 planning-with-files（PWF）v3.17.0 的文件规划与平台运行时为底座，构成独立衍生插件；默认增加现有项目文档维护、设计依据、验证与交接流程。上游高 star 不是兼容性或效果证据。

本规格替代 SPEC-0002 PD-01 的 0.1.0 单 Skill 实现限制、PD-02 的项目 AGENTS 显式启用前提，以及该规格的无新状态协议/CLI 与仅 TypeScript/Node.js 方向。承接 PD-03～07 的阅读、最小维护、证据和交接要求。SPEC-0001 REQ-09 的未来工具语言与平台方向由本规格重新决定；历史规格、ADR 和实验结果保留原适用范围。

安装后主 Skill 可以按任务自动匹配，但仍受用户要求、项目规则与宿主权限约束；自动匹配不保证每次触发，也不自动取得 hooks 信任。已有项目规则若保留启用条件，应照其约束执行。本仓库继续使用现有入口和计划，不因此正式启用或迁移自身文档体系。

## 运行与文档接口

Codex 继续从 `plugins/program-design` 分发；其他平台提供各自自包含包。主 Skill 整合 PWF 执行循环和文档规则，辅助能力使用宿主原生命令；不能禁止隐式调用的宿主由主 Skill 的显式子操作承接。语言变体保留独立布局，不作为同一个安装中的多个默认主入口。

同一会话只启用一套规划执行 hooks。doctor 报告其能实际检测的重复安装，不自动卸载另一插件。非 managed Codex hooks 的 trust、安装和实际上下文送达分别验证；不能依赖旧 validator 对 manifest `hooks` 字段的拒绝判断当前宿主能力。

多 Agent 沿用一个计划 owner；worker 使用分配文件或各自记录，不能竞写共享计划。独立任务绑定独立计划或 worktree。目标项目明确采用此流程时才把旧活跃计划状态入口一次性转向所选 PWF 计划，保留旧结果，不建立双向同步。普通文档更新仍由 Agent 使用已有工具完成，不增加独立写回引擎或自动归档服务。

hooks 私有缓存与项目记录分开核查。不宣称能从任意自然语言可靠识别只读意图；不具备模式识别能力的宿主，说明在启动会话前设置 `PLANNING_DISABLED=1`，并测试关闭后的行为。attestation 只验证摘要，不是人工批准；新读者检查与依据 review 的目的不同，不能相互替代。

## 验证与交付边界

交付 0.2.0 插件及各平台安装包、来源许可清单、确定性构建与检查入口、上游同步说明、兼容矩阵和复现记录。回归覆盖命名/根计划、拒绝错误绑定、多会话隔离、中文与空格路径、CRLF、只读边界、既有目录、批准需求冲突、证据不足和单一进度来源。

Linux、Windows、macOS 按可得环境分级验证。真实宿主用隔离配置验证安装、Skill 实际读取、注入、恢复、停止和卸载，并保留输入、输出及清理结果。无真实宿主或 OS 时记录 Not Run 与缺失条件，不表述为全平台运行通过。本轮不公开发布、不 push、不做个人全局安装，不实施 ADR-0003 所约束的自身正式接管。

设计决定与准确来源见 [ADR-0006](../adr/0006-pwf-derived-runtime.md)、[引用台账](../design-references.md)。
