# SPEC-0001：文档管理产品与资料基础

状态：基础阶段需求已接受；工具实现待后续设计。需求来源为用户在本任务确认的实施计划（2026-09-07）；不是从相关文章推断出的强制要求。

## 产品目标

让 Agent 能发现并复用项目文档、按任务读取、更新受影响的说明、保存交接状态和验证证据。新会话应能理解下一步，用户应能按指南完成核心操作。首批服务个人项目，保留以后开源与跨宿主适配的空间。

## 需求与验收

| 编号 | 已确认要求 | 本阶段验收 |
| --- | --- | --- |
| REQ-01 | 先建立依据，再设计工具；复杂度必须回应实际问题 | 引用和创新台账覆盖当前实质设计，候选机制未包装成产品功能 |
| REQ-02 | 两会话相关文章中文归档，保留来源 | 每项来源有收录去向、原链接、许可、整理范围和时效说明 |
| REQ-03 | 参考项目采用固定版本 submodule | 12 个 gitlink、`.gitmodules`、checkout 和索引 SHA 一致 |
| REQ-04 | 以文件为单位记录设计引用 | 第一方实质设计文件逐项关联问题、来源、差异和验证 |
| REQ-05 | 超出资料的机制先搜索，再记录创新 | 存在明确流程；暂无创新可为空，不制造原创性结论 |
| REQ-06 | 独立 subagent review 依据 | 审查原文/源码与创新记录，报告范围、状态和问题处理 |
| REQ-07 | 使用 specs、plans、ADR、reproduction 启动 | 各类文档承载本阶段真实目标、决定、进展和证据 |
| REQ-08 | 通用指令与个人差异分开并入库 | 根目录无个人 override，个人差异稿及组合说明可追溯 |
| REQ-09 | 后续工具面向 Codex、TypeScript/Node.js、Linux/Windows | 本阶段仅记录方向，不安装依赖或宣称兼容验证通过 |
| REQ-10 | 体系成熟后再管理自身文档 | 满足迁移 ADR 的验证条件后才切换 |

## 工具阶段的候选能力

接管已有文档、任务相关读取、普通文档增量更新、交接和证据维护仍是产品方向。具体文件布局、数据格式、CLI 命令、Skill 数量和 hooks 时机尚未定稿。

每项候选能力先给出一个实际问题或可复现场景，比较已有方案、普通 Markdown 工作流程和工具化方案；只选择能被验证的最小能力。角色 JSON、来源指纹、锁、`apply`、`doctor` 和安装器不能仅因前序讨论提到便直接实施。

未来按项目显式启用后，允许 Agent 在任务范围内维护普通文档；项目规则、权限和已批准需求的实质变更依照授权处理。普通维护不得为贴合代码而悄悄改写需求。

## 本阶段边界

后续行为验证已由用户于 2026-09-07 授权：执行独立交接测试、一次实际文档维护、依据 review 与验证，并据此决定首个工具功能。过程见 [PLAN-0002](../plans/0002-handoff-maintenance-baseline.md)。允许尝试已有本机 Agent 镜像并清理本轮临时资源；这不改变产品候选机制尚未定稿的状态。

该轮已完成，结果支持继续现有 Markdown/Git 流程；本轮暂缓 CLI，首要候选为只读检查入口，详见 [ADR-0004](../adr/0004-defer-product-cli-after-baseline.md)。这不改变后续 TypeScript/Node.js 和双平台方向。

当前交付资料、规范、引用与 review，不创建可执行产品或部署服务。参考项目的说明只能证明上游宣称或实现了某种机制；没有运行其测试时，不记为本仓库已验证。
