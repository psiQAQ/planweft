## 原文译文

Codex 和 `gpt-5.2-codex` 模型（原文推荐）可用于实现需要大量时间研究、设计和实施的复杂任务。本文的方法是指导模型完成这类任务的一种方式。

这些计划既是详尽的设计文档，也是持续更新的“活文档”。作为 Codex 用户，你可以在它开始长时间实施前，用计划检查其准备采用的方法。下面给出的 `PLANS.md` 与一份曾让 Codex 从单个提示持续工作七个多小时的文件非常相似。

要让 Codex 使用这些文档，先更新 `AGENTS.md`，说明何时使用 `PLANS.md`，再把 `PLANS.md` 加入仓库。

### AGENTS.md

[`AGENTS.md`](https://github.com/openai/agents.md) 是指导编码 Agent 的简单格式。我们定义一个可用作简称的术语，并给出何时使用计划文档的简单规则。这里称之为“ExecPlan”。这是任意选取的名称，Codex 并没有针对它接受训练。使用提示时，可以通过这个简称指向特定的计划定义。

下面是在 `AGENTS.md` 中规定计划使用时机的示例：

```md
# ExecPlans

编写复杂功能或进行重大重构时，从设计到实现都使用 ExecPlan（定义见 .agent/PLANS.md）。
```

### PLANS.md

以下是完整文档。这里的提示词经过专门选择，以便向用户提供足够反馈，并指导模型准确实施计划。用户可以按自己的需要调整文件，增加或移除必需章节。

~~~md
# Codex 执行计划（ExecPlans）

本文规定执行计划（ExecPlan）的要求。它是一份设计文档，编码 Agent 可以按照它交付可运行的功能或系统变更。将读者视为完全不了解本仓库的新手：他们只有当前工作树和你提供的这一份 ExecPlan，没有先前计划的记忆，也没有外部上下文。

## 如何使用 ExecPlans 和 PLANS.md

编写可执行规格（ExecPlan）时，严格遵守 PLANS.md。如果它不在上下文中，完整阅读它以恢复记忆。充分阅读、必要时重读源材料，以形成准确规格。新建规格时先从骨架开始，随着研究逐步补全。

实施 ExecPlan 时，不要向用户询问“下一步”，直接进入下一个里程碑。持续更新所有章节，在每个停下来的位置添加或拆分清单项，明确已取得的进展和下一步。自主解决歧义，并频繁提交。

讨论 ExecPlan 时，在规格中的日志里记录决定，使以后的人清楚理解为什么修改规格。ExecPlan 是活文档，应始终能仅凭这一份文件重新开始工作。

研究具有困难需求或显著未知因素的设计时，用里程碑安排概念验证、小型试作等，检验用户提议是否可行。阅读待使用库的源码，必要时获取源码，深入研究，并用原型指导完整实现。

## 要求

不可协商的要求：

* 每份 ExecPlan 都必须完全自包含，即它当前的版本包含让新手成功所需的全部知识和指令。
* 每份 ExecPlan 都是活文档。随着进展、发现和设计决定形成，贡献者必须修订；每次修订仍需完全自包含。
* 每份 ExecPlan 必须让完全不了解仓库的新手端到端实现功能。
* 每份 ExecPlan 必须产生可证明有效的行为，而不只是为“符合某个定义”修改代码。
* 每份 ExecPlan 必须用普通语言解释所有专业术语，否则就不要使用它们。

目的和意图优先。先用几句话从用户角度说明工作为何重要：变更之后能做什么以前做不到的事，以及如何观察它确实有效。然后给出达成结果的准确步骤，包括修改什么、运行什么、应看到什么。

执行计划的 Agent 能列出、阅读和搜索文件，运行项目和测试。它不了解先前上下文，也不能从较早里程碑推断你的意思。重述你依赖的假设。不要把必需知识外包给博客或文档链接；用自己的话将其写进计划。若计划建立在已入库的先前 ExecPlan 上，可以引用那份文件；否则必须纳入它的全部相关上下文。

## 格式

格式与外层包装简单而严格：每份 ExecPlan 必须放在一个标为 md 的代码围栏内，由三个反引号开头和结尾。不要在里面嵌套另一个三反引号围栏；需要展示命令、执行记录、diff 或代码时，在外层围栏中使用缩进块，避免提前关闭围栏。每个标题后留两个换行，使用 #、## 等标题以及正确的有序和无序列表语法。

如果写入 Markdown 文件的全部内容就是单个 ExecPlan，则省略外层三反引号。

用普通段落书写，优先句子而非列表。除非简略表达会损害含义，否则避免清单、表格和长枚举。只有 Progress 章节允许并且必须使用检查清单；叙述章节仍以段落为主。

## 指导原则

自包含和普通语言最重要。如果引入非常用术语，如 daemon、middleware、RPC gateway、filter graph，应立即解释，并说明它在本仓库中对应什么，例如指出有关文件或命令。不要只写“如前定义”或“参见架构文档”；在此提供必要解释，即使有所重复。

避免常见失败：不依赖未定义术语，不把功能表面要求写得过窄，导致代码编译成功却没有实际作用，也不把关键决定交给读者。存在歧义时，在计划中解决并说明原因。宁可多解释用户可观察的效果，少规定偶然的实现细节。

用可观察结果锚定计划：说明实现后用户能做什么、要运行哪些命令、看到什么输出。验收表达应是人能检查的行为，例如“启动服务后访问 http://localhost:8080/health 返回 HTTP 200，正文为 OK”，而不是“增加了 HealthCheck struct”这类内部属性。内部改动也要说明如何展示效果，例如原先失败而修改后通过的测试，以及使用新行为的场景。

明确仓库上下文。用完整的仓库相对路径指明文件，准确命名函数和模块，说明新文件应建在哪里。涉及多个区域时，用短段落解释它们如何衔接，帮助新手定位。运行命令时给出工作目录和准确命令；依赖环境条件时说明假设，并在合理时提供替代方法。

步骤应幂等且安全：多次执行不会造成破坏或漂移。若某一步可能中途失败，说明如何重试或调整。迁移或破坏性操作需要明确备份和安全退路。优先采用可以边做边验证的增量修改。

验证不是可选项。说明如何运行测试、适用时如何启动系统，并观察它完成有用的工作。为新功能或能力提供全面的测试说明，以及预期输出和错误信息，让新手辨别成败。尽可能展示超越编译的效果证明，例如小型端到端场景、CLI 调用或 HTTP 请求响应记录。给出适配项目工具链的准确测试命令和结果解释。

保存证据。步骤产生终端输出、小型 diff 或日志时，在单个围栏中以缩进示例记录，保持简洁并聚焦成功证据。需要补丁时，优先文件级 diff 或可以按说明重建的小片段，而不是大块粘贴。

## 里程碑

里程碑是叙述，不是繁文缛节。若分阶段工作，每个里程碑用短段落说明范围、结束时新增了什么、运行什么命令、预期何种验收。按目标、工作、结果、证明组织。进度与里程碑不同：前者跟踪细项，后者讲清工作过程；两者都要有。不要只为简短而省略未来实施者可能需要的细节。

每个里程碑都必须可独立验证，并逐步实现整个执行计划的目标。

## 持续更新的计划与设计决定

* ExecPlan 是活文档。做出关键设计决定时，更新计划并记录决定及理由，全部放入 Decision Log。
* 必须包含并维护 Progress、Surprises & Discoveries、Decision Log 和 Outcomes & Retrospective 四个章节。
* 发现影响方案的优化器行为、性能取舍、意外 Bug 或反向/撤销语义时，在 Surprises & Discoveries 中记录，附简短证据，最好是测试输出。
* 实施中改变方向时，在 Decision Log 解释原因，并在 Progress 反映影响。计划既是自己的清单，也是下一位贡献者的指南。
* 大任务或整个计划结束时，在 Outcomes & Retrospective 总结成果、剩余事项和经验。

# 原型里程碑与并行实现

当明确的原型阶段能降低大改动风险时，可以且常常值得采用。例如给依赖增加底层操作验证可行性，或比较两种组合次序并测量效果。原型保持增量、可测试；明确标注“原型”，说明如何运行和观察，以及何时采用或放弃。

优先先增加代码，再在测试保持通过的前提下移除旧代码。若能降低风险或保持大迁移期间测试可用，可以并行保留两套实现，例如新适配器与旧路径。说明如何验证两条路径以及如何安全移除其中一条。面对多个新库或功能区域时，可分别开展小型探索，独立证明外部库能按预期运行并提供所需能力。

## 一份良好 ExecPlan 的骨架

    # <简短、面向行动的描述>

    本 ExecPlan 是活文档。工作过程中持续更新 Progress、Surprises & Discoveries、Decision Log 和 Outcomes & Retrospective。

    若仓库有 PLANS.md，在这里写出相对于仓库根目录的路径，并说明按它维护本文。

    ## Purpose / Big Picture

    用几句话说明变更带来的价值，以及用户如何看到它生效。写清要实现的可观察行为。

    ## Progress

    用复选框列表总结细步骤。每次暂停都记录在这里，即使要把部分完成的任务拆为“已完成”和“剩余”。本节必须反映实际状态。

    - [x] (2025-10-01 13:00Z) 已完成步骤示例。
    - [ ] 尚未完成步骤示例。
    - [ ] 部分完成步骤示例（已完成 X；剩余 Y）。

    用时间戳衡量进度速率。

    ## Surprises & Discoveries

    记录实施中遇到的意外行为、Bug、优化或新认识，并附简短证据。

    - Observation: …
      Evidence: …

    ## Decision Log

    按下列格式记录工作期间的每个决定：

    - Decision: …
      Rationale: …
      Date/Author: …

    ## Outcomes & Retrospective

    在重要里程碑或结束时总结结果、缺口和经验，并与最初目的比较。

    ## Context and Orientation

    假设读者毫无背景，描述当前任务相关状态。给出关键文件和模块完整路径，解释不直观术语，不依赖先前计划。

    ## Plan of Work

    用段落说明修改和新增的顺序。每项改动给出文件、函数或模块位置，以及插入或修改什么。具体且最小。

    ## Concrete Steps

    说明准确命令和执行目录。命令有输出时给出简短预期记录供比较；随着进展持续更新。

    ## Validation and Acceptance

    描述如何启动或操作系统，以及应该观察什么。用具体输入输出表达行为验收。涉及测试时写明项目测试命令、预期通过数量，以及新测试在修改前失败、修改后通过。

    ## Idempotence and Recovery

    若可安全重复执行则说明；有风险的步骤给出重试或回退路径。结束后保持环境整洁。

    ## Artifacts and Notes

    用缩进示例保存最重要的执行记录、diff 或片段，简洁聚焦成功证据。

    ## Interfaces and Dependencies

    明确规定要用的库、模块和服务及其理由，写清里程碑结束时必须存在的类型、trait/interface 和函数签名。优先稳定的名称和路径，如 crate::module::function 或 package.submodule.Interface。例如：

    在 crates/foo/planner.rs 中定义：

        pub trait Planner {
            fn plan(&self, observed: &Observed) -> Vec<Action>;
        }

遵循以上指导后，一个无状态 Agent 或人类新手应能从头到尾读完 ExecPlan，产出可运行、可观察的结果。标准是：自包含、自足、能够引导新手、面向结果。

修订计划时，确保改动完整反映到所有章节，包括持续更新的部分，并在计划底部说明改了什么、为什么改。ExecPlan 对几乎所有事项都需要说明“为什么”，不只是“是什么”。
~~~
