# Overlay assembly contract

These files are local extension sources, not another Skill implementation. The build retains the upstream Skill/runtime and generates every distribution from the same pinned source plus this overlay.

1. Insert `workflow.md` immediately after each main Skill's YAML frontmatter, before the upstream body. Rename the main Skill to `project-docs` and set its description to automatic matching for substantive implementation, maintenance and continuation of documented work; state that reading and planning-only tasks remain read-only. Do not carry forward the 0.1.0 project-opt-in requirement. Localized main Skills can share this English precedence section while retaining their upstream localized body.
2. Copy `references/evidence.md` to `references/evidence.md` next to each main Skill, including standalone Skills. The workflow link is relative to that installed Skill.
3. Append `templates/task_plan.append.md` to `templates/task_plan.md`, `task_plan_autonomous.md` and `analytics_task_plan.md` when present. Append `findings.append.md` to `findings.md` and `analytics_findings.md`, and `progress.append.md` to `progress.md`. Preserve upstream headings, phase order, `**Status:**` literals and original content. Append exactly once during generation from pristine sources, never repeatedly to generated files. The fragments introduce no phase, status token or checkbox that changes runtime completion counts.
4. Upstream ordinary `init-session.sh`/`.ps1` initializes compact embedded records rather than copying ordinary template files. The workflow therefore instructs the Agent to add only useful fields after initialization; do not claim the initializer automatically uses these expanded templates. A build that patches embedded initialization must separately test both new-file creation and preservation of existing files.
5. `README.md` is self-contained package-level explanation material. Keep it available alongside adapter-specific installation/compatibility instructions, avoiding replacement of needed native activation details.
6. These extension files do not choose the command alias map. Apply the build's single identity mapping to all retained upstream implementation, command and install paths; preserve upstream links and attribution as source identity. The extension assumes only `project-docs`, `pd-` helper commands, `pd_` OpenCode tools and unchanged PWF environment/disk protocols.
7. Generate version 0.3.0 as fourteen self-contained `dist/<host>/program-design/` directories. Do not generate ZIP archives. Retain `plugins/program-design/` as the Codex compatibility mirror, and generate each supported host's own repository-root catalog with `name` metadata `program-design`; the host's actual registered identifier can depend on its source and must be read back. Catalog paths must resolve to the corresponding host payload; source registration does not install or trust a plugin.
8. Native wrappers must use their own installed root to find package assets. Keep target project records separate. Gemini uses `gemini-extension.json`, `hooks/hooks.json` and `${extensionPath}` substitution. Hermes pairs its root plugin with `skills/project-docs/`. Kiro wraps its own Skill as a skills-only Power. Factory and CodeBuddy expose their native Skill without carrying unverified executable frontmatter hooks into automatic activation.
9. The normal Python build remains offline and standard-library-only. OpenCode V1 runtime JavaScript is compiled separately through `scripts/compile-opencode.py --install`; the retained intermediate output is bound to its source digest. `--check --install` recompiles with the locked dependencies in a temporary location and checks it. A stale intermediate output is a build error, not permission to ship uncompiled TypeScript. Pi uses its native package runtime.
10. Release preparation writes a new output directory outside the checkout only; `--previous-release` continues the prior generated branch history. Repository URL and npm scope must be supplied together when remote coordinates are requested. The regular build supplies repository marketplace files; release preparation packs Pi/OpenCode npm archives and Gemini/Hermes branch-root payloads. Without an actual repository URL and npm identity, document local use and missing publication configuration. Do not push, publish, install a host plugin or change user configuration as part of building or preparing.

Verify all installed reference links, descriptions and fragment counts; run parser tests against expanded templates; verify the exact file inventory, bytes and executable modes of directories and catalog targets. Check npm file allowlists and precompiled entries. Distinguish these checks from actual Agent behavior and installation/update validation.

## Public documentation sources

Maintain each public document in Chinese and English. Edit installation text only in `install/INSTALL.md` and `install/INSTALL.en.md`; the builder generates `docs/installation.md`, `docs/installation.en.md` and each platform's matching INSTALL pair. The repository mirrors adapt relative navigation, while installed copies remain self-contained. Both are included in `--verify`; unrelated files in docs are preserved.

The README pair in this overlay supplies package introductions. The repository's README pair provides the broader project overview, comparison and attribution; `docs/platforms.md` / `platforms.en.md` explain cross-platform design. Root documentation is not a runtime dependency. Pi/OpenCode npm packages include both README and INSTALL languages, and OpenCode's compilation manifest is refreshed when its packaging inputs change.
